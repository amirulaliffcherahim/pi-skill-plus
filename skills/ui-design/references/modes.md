# Mode playbooks

Condensed from impeccable's mode guides (see NOTICE.md). Pick the mode from the requested surface, then use its playbook.

## Operate (app UI, dashboards, tools)
A user came to get a job done. The page is a working product of its category first.
- The visual world lends only **type, palette, density and one signature move**. It never supplies layout, navigation model or controls.
- Use standard controls the visitor already knows: buttons, tabs, inputs, selects, filters, sortable tables, navigation that reads as navigation. Never a costume of the world's own interface (terminal function-key bars, instrument bezels, ledger paper standing in for a table).
- Colour does real jobs: a committed shell palette, state colours (red critical, amber degraded), data series, selection. Grey plus one accent is the category default, not restraint.
- Design the shell first: navigation, work areas and what each is for, the data read first and its states, then where the signature move lives. Name the move concretely (service health drawn as a transit map).
- Use real content: product name, plausible values and units, real labels, one state worth seeing (alert, empty filter result). A headline number that changes over time shows recent history.
- Variants differ in organisation (side rail / top bar / command-first, density, which data leads), not in world coverage.
- Self-check: with the name covered, does it read as a product of its category, can the task be done from it, is it at least as clean as the category standard?

## Read (docs, articles, guides, changelogs)
The visitor came to understand something.
- The world owns the **frame**: masthead, nav rail, ground, title and section openers, how code/tables/callouts are set. The **column stays calm**: a reading face, real contrast, 60-75ch (about 16px body), nothing performing behind the text.
- Never replace navigation with something a reader must learn. Docs read as docs, a guide as a guide.
- Good sources: reference books, type specimens, timetables, field guides, manuals, a newspaper's wayfinding. Not tool or instrument interfaces (they come back as costumes).
- Monospace is for code, parameters and small labels, never running text or headings by default.
- Show where the reader stands, the opening that answers the question, section headings, next/previous.
- Test with real material: actual title, opening paragraph, section names, and the hardest content the surface holds (code sample, reference table, diagram).
- Self-check: can a reader tell where they are and read comfortably? If the page reads as an artifact of the world before a document, pull the world back to the frame.

## Persuade (landing, marketing, pricing)
Design is the product. Commit.
- The first view makes the offer intelligible and desirable, exposes the action the category's visitors came for **in its working form** (route-and-dates search, open appointment slots, add to cart), and shows something only this product can prove. A decorative link pointing elsewhere does not count.
- The world is the **carrier** of the page, never a picture of it. Its material is the ground and major surfaces and its type sets headlines; a world reduced to an accent on a neutral template is the default with a sticker on it. But parts still work as parts: nav reads as links, copy is set text, the action is plainly clickable, sections keep a steady rhythm.
- Avoid both ends: the painted poster with no working parts, and the generic template (headline over subcopy and button, row of equal cards, split hero with badge row).
- When the world is an object, show that one object once at one scale; it keeps its real form.
- Ship real imagery when the brief needs it. Label illustrative values honestly.

## Experience (portfolio, gallery, showcase)
The work leads from the first viewport. The interface recedes: minimal chrome, fast access to the artifact, no decoration competing with it.
